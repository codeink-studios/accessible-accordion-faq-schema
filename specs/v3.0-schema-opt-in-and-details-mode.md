# v3.0 — Schema opt-in + native `<details>` mode

> [!info] Triggered by
> Joost de Valk's [FAQ schema cycle](https://joost.blog/faq-schema-cycle/) (May 2026). Google removed FAQ rich results from Search on 7 May 2026; full removal slated for June 2026. The markup itself remains valid schema.org and is still consumed by Bing and (plausibly) AI search surfaces — so we're not killing the schema feature, we're making it opt-in.

## Decisions locked

1. **Schema emission becomes opt-in, default off for new blocks.** Single toggle, not a 3-mode select. Operator decides per-block whether the FAQ block represents the page's primary content (or whether they want to give AI surfaces structured Q/A signal).
2. **Existing v2.x blocks preserve current behavior on upgrade.** Schema stays on, JS-accordion mode stays as the only collapsible variant for blocks already saved. No silent regressions.
3. **Native `<details>`/`<summary>` mode added as the recommended collapsible variant for new blocks.** The existing JS-button mode (~0.5KB script) stays for backward compatibility on existing posts. New v3.x inserts default to the no-JS native variant.
4. **Plugin name + marketing unchanged.** GEO / LLM ingestion case for FAQ schema remains plausible enough to keep the feature positioned. Only the factually-wrong `readme.txt` FAQ entry about Google rich results gets rewritten.
5. **No activation notice, no admin banner.** Changelog + upgrade-notice text in `readme.txt` is the only operator-facing comms.

## Block attributes (parent)

Adding to [[../src/faq-block/block.json|`src/faq-block/block.json`]]:

| Attribute | Type | Default | Purpose |
|---|---|---|---|
| `enableSchema` | boolean | `false` | Whether to emit `FAQPage` JSON-LD. v2.x blocks force `true` via legacy gate. |
| `useNativeDetails` | boolean | `false` | When `collapsible` is true, use native `<details>`/`<summary>` instead of `<button>` + JS. |
| `blockVersion` | number | `0` | Migration marker. Legacy v2.x blocks have no value (treated as 0). v3.x blocks get `3` set explicitly. |

`providesContext` adds `cis/accessible-accordion-faq/useNativeDetails` so the child block knows which markup branch to render.

## Migration logic

The hard problem: v2.x blocks (schema-on, JS-accordion) and a brand-new v3.x insert with default toggles (schema-off, native-details) both arrive at the server with no explicit `blockVersion` attribute. We have to differentiate them.

**Two-stage gate:**

### Editor-side (parent block `edit()`, run once on mount)

```js
if (blockVersion < 3) {
  const hasLegacyContent = innerBlocks.some(
    item => (item.attributes?.question || '').trim() !== ''
  );
  if (hasLegacyContent) {
    // v2.x block opened in v3 editor → preserve current behavior.
    setAttributes({ blockVersion: 3, enableSchema: true, useNativeDetails: false });
  } else {
    // Fresh v3 insert (template-stub child, no real Q/A yet) → v3 defaults.
    setAttributes({ blockVersion: 3, enableSchema: false, useNativeDetails: true });
  }
}
```

Heuristic: legacy blocks always have at least one filled-in `question` because they couldn't have been saved without one. A template-stub child from `[ [ 'cis/faq-item' ] ]` has `question: ''`. Edge case: a legacy block where the user deleted all questions but kept the block — unlikely in practice, would migrate as "fresh." Documented as known limitation.

### Server-side (parent `render.php`, every render)

For pages that are rendered before any editor touch (e.g., cached pages on a site that upgrades the plugin but doesn't open the post):

```php
$block_version = isset( $attributes['blockVersion'] ) ? (int) $attributes['blockVersion'] : 0;
if ( $block_version < 3 ) {
    // Legacy v2.x: preserve old behavior.
    $enable_schema       = true;
    $use_native_details  = false;
} else {
    $enable_schema       = ! empty( $attributes['enableSchema'] );
    $use_native_details  = ! empty( $attributes['useNativeDetails'] );
}
```

Result: legacy blocks behave identically until the post is opened in the v3 editor (which writes `blockVersion: 3` plus preserved defaults). After that, the server-side gate stops applying and the explicit attributes carry forward.

## Markup output by mode

### Mode A: Open (collapsible off) — unchanged

```html
<div id="faq" class="cis_accordion">
  <dl class="cis_accordion__list">
    <dt class="cis_accordion__question">Question</dt>
    <dd class="cis_accordion__answer"><p>Answer</p></dd>
  </dl>
  <!-- JSON-LD only if enableSchema=true -->
</div>
```

### Mode B: Collapsible JS-accordion (legacy / opt-out) — unchanged

```html
<div id="faq" class="cis_accordion cis_accordion--collapsible">
  <dl class="cis_accordion__list">
    <dt class="cis_accordion__question">
      <button class="cis_accordion__trigger" type="button" aria-expanded="false" aria-controls="…">…</button>
    </dt>
    <dd class="cis_accordion__answer" role="region" aria-labelledby="…" hidden>…</dd>
  </dl>
  <!-- JSON-LD only if enableSchema=true -->
</div>
```

### Mode C: Collapsible native `<details>` (new, recommended for v3.x)

```html
<div id="faq" class="cis_accordion cis_accordion--collapsible cis_accordion--native">
  <div class="cis_accordion__list">
    <details class="cis_accordion__item">
      <summary class="cis_accordion__question">Question</summary>
      <div class="cis_accordion__answer"><p>Answer</p></div>
    </details>
  </div>
  <!-- JSON-LD only if enableSchema=true -->
</div>
```

Note: `<details>` cannot live inside `<dl>` per the HTML spec, so this mode swaps the list wrapper from `<dl>` to `<div>`. Zero JavaScript enqueued.

## Editor UX

In the **FAQ settings** panel:

1. **Title heading level** — existing, unchanged.
2. **Collapsible (accordion)** — existing toggle, unchanged.
3. **Use native `<details>` element** — new, indented under Collapsible, only visible when Collapsible is on. Help text: "Uses the browser's native disclosure element. No JavaScript. Recommended for new sites."
4. **Enable FAQ schema (JSON-LD)** — new, in the Schema panel. Default off. Help text: "Off by default. Enable when this FAQ block is the primary content of the page, or when you want to give AI search engines structured Q/A signal. Google removed FAQ rich results from Search in May 2026, but the markup remains valid structured data."

The existing **Schema & linking** panel changes from a static info paragraph into the schema toggle plus a help paragraph.

## Out of scope (deferred)

- `acceptedAnswer` → `answer` property switch. Not a valid schema.org property yet.
- `FAQSection` type emission. Not a real schema.org type yet.
- Removing the JS-accordion mode entirely. Kept for backward compatibility; revisit in v4 if usage analytics ever justify it.

## Known limitations

- A v2.x block with all questions deleted (but block still present) will migrate as "fresh insert" — schema off, native details on. Considered acceptable: an FAQ with no questions wasn't rendering anything meaningful anyway (server-side render returns empty when `$cis_aafs_schema_items` is empty).
- The native `<details>` mode's expand-animation is whatever the browser provides. The CSS-driven animation in the JS mode (180ms fade + slide gated behind `prefers-reduced-motion`) won't apply to the native variant because `<details>` open/close isn't transitionable in current browsers without `@starting-style` + `interpolate-size`. Tradeoff for zero-JS simplicity.
