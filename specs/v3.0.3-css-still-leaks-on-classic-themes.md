# v3.0.3 — Frontend CSS still leaked on classic themes

> [!warning] The v3.0.2 fix did not hold
> v3.0.2 replaced the `block.json` `"style"` key with `wp_enqueue_block_style()` on the belief that the latter "guarantees the stylesheet is only emitted on pages where the block actually renders" (comment previously at [[../accessible-accordion-faq-schema.php|the main plugin file]], lines 41–44). WordPress core makes no such guarantee. On a classic theme the call falls back to a site-wide enqueue — the same leak, reached by a different route.

## Root cause

`wp_enqueue_block_style()` in `wp-includes/script-loader.php`:

```php
$hook = did_action( 'wp_enqueue_scripts' ) ? 'wp_footer' : 'wp_enqueue_scripts';
if ( wp_should_load_block_assets_on_demand() ) {
    add_filter( 'render_block', $callback_separate, 10, 2 );  // conditional path
    return;
}
add_action( $hook, $callback );  // ← global fallback: every page
```

`wp_should_load_block_assets_on_demand()` defaults to the return value of `wp_should_load_separate_core_block_assets()`, which is **false on classic (non-block) themes** unless the theme or another plugin opts in. So on any classic-theme site the conditional branch is never taken and the stylesheet is enqueued on every page whether or not the block is present.

Block themes were never affected — they take the `render_block` branch, which works correctly.

## Verification that reproduced it

Production classic-theme site running v3.0.2 (version confirmed from the served `readme.txt` Stable tag). Classic theme confirmed by the presence of the `classic-themes` stylesheet and a single monolithic `wp-block-library-css` rather than per-block stylesheets.

| Page | Block present in markup | `cis-aafs-style` emitted |
|---|---|---|
| A post with no FAQ block | no | yes |
| Homepage | no | yes |
| Contact page | no | yes |

The stylesheet appeared inlined as `<style id="cis-aafs-style-inline-css">` because the plugin passes `path`, making it eligible for core's `wp_maybe_inline_styles()`. That inlining is intended and harmless — the defect was that it was enqueued at all.

## Options considered

> [!failure] Rejected — opt in to on-demand loading
> `add_filter( 'should_load_separate_core_block_assets', '__return_true' );` would make `wp_enqueue_block_style()` behave as assumed. Rejected: a plugin must not flip a site-wide asset-loading strategy on the host theme's behalf. On a classic theme it also changes how *core* block CSS is delivered and can visibly alter styling site-wide.

> [!success] Shipped — enqueue from the block's render callback
> Register the stylesheet on `init` with `wp_register_style()` + `wp_style_add_data( …, 'path', … )`, and call `wp_enqueue_style( 'cis-aafs-style' )` inside [[../src/faq-block/render.php|`src/faq-block/render.php`]], after the early return for blocks with no complete Q/A pairs. `render.php` only executes when the block is on the page and has something to show, so the CSS cannot load anywhere else. Behaviour is identical on block themes.

## Consequences

- The stylesheet now loads in the **footer** rather than `<head>`, because it is enqueued during `the_content` rendering. Core hooks `wp_maybe_inline_styles()` on `wp_footer` priority 1 specifically to catch late-enqueued styles, so it is still inlined and there is no extra request.
- A block with no complete Q/A pairs already returns `''` and now also enqueues nothing — correct, and slightly better than before.
- No attribute, markup, or editor changes. No migration.
