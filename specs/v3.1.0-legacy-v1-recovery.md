# v3.1.0 — Recover FAQ blocks destroyed by the v1 to v2 restructure

> [!failure] v2.0.0 shipped a breaking structural change with no migration
> Every FAQ built before v2.0.0 silently stopped rendering the moment a site upgraded, and was destroyed permanently the first time an affected post was opened and saved. This went unnoticed from v2.0.0 (2026-05) until 2026-07-28.

## What broke

v1.x stored the whole FAQ in a **single self-closing block**. Every Q/A pair lived in a `faqs` array attribute; there were no child blocks:

```
<!-- wp:cis/accessible-accordion-faq {"title":"FAQ","faqs":[{"question":"…","answer":"…"}]} /-->
```

v2.0.0 restructured to parent + `cis/faq-item` InnerBlocks children. Its own commit message calls it a breaking change. It shipped **zero deprecations** — `deprecated` was absent in v2.0.0 and still absent through v3.0.3.

Consequences from v2.0.0 onward:

1. **Front end:** [[../src/faq-block/render.php|`render.php`]] walks `innerBlocks`, finds none, `$cis_aafs_has_complete` stays false, returns `''`. The FAQ renders as nothing.
2. **Editor:** the block parses as *valid* (its `save` is `InnerBlocks.Content`, which over zero children serializes to nothing — matching the empty stored content), so no invalid-block warning ever appeared. It just looked empty.
3. **On save:** `faqs` is no longer a declared attribute, so it is dropped on re-serialization. The data is gone for good.

Step 3 is the reason this is time-sensitive: until an affected post is opened **and saved**, the content is still sitting in `post_content` and is fully recoverable.

## Why a plain deprecation would not have fired

Deprecations are normally triggered by save-output validation failure. These blocks are *valid*, so nothing triggers. `isEligible` is the documented opt-in for exactly this case — "a function which returns `true` if the deprecation can handle the block migration even if the block is valid."

Confirmed against `packages/blocks/src/api/parser/apply-block-deprecated-versions.ts`:

```js
const parsedAttributes = rawBlock.attrs ?? {};
…
if ( block.isValid && ! isEligible( parsedAttributes, block.innerBlocks, { blockNode: rawBlock, block } ) ) {
    continue;
}
…
attributes: getBlockAttributes( deprecatedBlockType, block.originalContent ?? '', parsedAttributes )
```

Two properties this relies on:

- `isEligible` receives `rawBlock.attrs` — the **raw block-comment JSON** — so `faqs` is visible even though the current schema has no such key.
- `migrate` receives attributes re-parsed through the **deprecation's own** attribute schema, so declaring `faqs` there populates it.

## Shipped

**1. Editor-side deprecation** ([[../src/faq-block/index.js|`src/faq-block/index.js`]]) — `isEligible` detects legacy `faqs` data with no children; `migrate` rebuilds `cis/faq-item` children with `core/paragraph` answers, preserving title, heading level, collapsible mode, and anchor. Sets `enableSchema: true` (v1 had no toggle and always emitted JSON-LD) and stamps `blockVersion: 3`.

`isEligible` is deliberately strict — it returns false the moment any inner block exists. A false positive would replace a working block's children with nothing, turning a display bug into real data loss.

**2. Server-side rescue** ([[../src/faq-block/render.php|`render.php`]] + helpers in the main plugin file) — when the modern path finds no complete pairs and a legacy `faqs` attribute is present, render directly from it. This is what makes recovery work **without touching a single post**: affected FAQs reappear on the front end on update. Recovered rows render in current markup (native `<details>` in collapsible mode), not the retired v1 JS accordion.

**3. Editor script cache-bust** — `index.asset.php` `version` had been stale at `3.0.1` since that release. A cached `index.js` would mean the deprecation never loads, so the migration would silently not run. Now tracks the plugin version.

**4. Regression tests** ([[../tests/README|`tests/`]]) — 47 assertions, no WordPress or npm required. Excluded from the release ZIP.

## Order of operations for affected sites

1. Update to 3.1.0. Front end recovers immediately, no editing.
2. Then open affected posts. Opening converts to the current structure; saving makes it permanent.

Doing this in the other order — opening a post on ≤3.0.3 and saving — destroys that post's FAQ irrecoverably.

## Follow-up

No deprecation covers the v3.0.0 → v3.0.1 removal of `useNativeDetails`. That one is cosmetic rather than destructive (the attribute is dropped, native `<details>` is now the only mode), so it is left alone deliberately — noted here so the omission is a decision rather than another oversight.
